Proiect #2 
Break the Login – Atacarea și securizarea autentificării 
 
Obiectiv Scopul proiectului este ca studentul să înțeleagă cum este atacat în practică 
un sistem de autentificare și cum trebuie implementat corect pentru a rezista 
atacurilor reale. 
Studentul va: 
• construi un mecanism de autentificare funcțional, dar inițial 
vulnerabil; 
• demonstra exploatarea lui prin tehnici de ethical hacking; 
• remedia vulnerabilitățile prin implementarea controalelor corecte de 
securitate; 
• valida că atacurile nu mai funcționează după fix. 
Accentul cade pe: 
• logică de autentificare; 
• parole; 
• sesiuni / token-uri; 
• resetare parolă; 
nu pe funcționalități de business complexe. 
Scenariu Compania fictivă “AuthX” dezvoltă o aplicație internă folosită de angajați 
pentru acces la resurse sensibile. 
Aplicația este deja folosită în producție, dar echipa de securitate a semnalat 
probleme serioase legate de autentificare. 
Studentul joacă dublu rol în proiect: 
• Security tester – identifică și demonstrează vulnerabilitățile; 
• Developer – repară implementarea și întărește sistemul. 
Auditul se concentrează exclusiv pe: 
• login; 
• gestionarea parolelor; 
• sesiuni; 
• resetarea parolei.

Structură minimă de bază de date (nivel mediu, realist) 
 
1. Tabelul users 
Câmp Tip (exemplu) Descriere 
id int / uuid (PK) Identificator unic utilizator 
email string (unique) Username / email 
password_hash string Hash parolă (bcrypt / argon2) 
role enum ANALYST / MANAGER 
created_at timestamp Data creării contului 
locked boolean Cont blocat (brute-force) 
 
2. Tabelul tickets 
Câmp Tip Descriere 
id int / uuid (PK) Identificator ticket 
title string Titlu ticket 
description text Conținut (posibil XSS dacă nu e tratat) 
severity enum LOW / MED / HIGH 
status enum OPEN / IN_PROGRESS / RESOLVED 
owner_id FK → users.id Cine a creat ticket-ul 
created_at timestamp Data creării 
updated_at timestamp Ultima modificare 
owner_id este cheia pentru prevenirea IDOR.

3. Tabelul audit_logs 
Câmp Tip Descriere 
id int / uuid (PK) Identificator eveniment 
user_id FK → users.id Cine a făcut acțiunea 
action string LOGIN / CREATE_TICKET / etc 
resource string ticket / auth / audit 
resource_id string ID-ul resursei afectate 
timestamp timestamp Când s-a întâmplat 
ip_address string IP (pentru realism) 
 
Relațiile dintre tabele (foarte important pentru securitate) 
Relație De ce contează 
users → tickets (1:N) Permite verificarea ownership-ului 
users → audit_logs (1:N) Cine a făcut ce 
tickets → audit_logs (1:N) Ce s-a întâmplat cu un ticket 
 
Cum este folosită DB în fluxul de securitate 
Funcționalitate Ce verifici în DB 
Login User + password_hash 
View ticket ticket.owner_id == user.id 
Edit ticket Rol + ownership 
Search Query parametrizat 
Audit Insert la fiecare acțiune 
Brute force Cont blocat după N încercări 
 
Ce DB puteți utiliza? 
Opțiune De ce e bună 
PostgreSQL SQL real, bun pentru injection labs 
MySQL Foarte comun în industrie 
SQLite Simplu, local, suficient pentru proiect 
MongoDB Acceptabil dacă vrei NoSQL injection 
 
Recomandare pentru curs: PostgreSQL sau SQLite, ca să rămână ușor de rulat local
